# 設計: 文のつながりで論理構造を可視化する

(2026-08-04 に textmining プロジェクトで記録し，
2026-08-10 にこのリポジトリへ移した)

## 目的

単語のつながりによって，文章の論理的な構造を明確にする R パッケージを作る．

- 前方の文と同じ単語があれば，その単語でつなげて文章を表示する．
- 前方(および後方)の文と共通の単語がまったくない文は，
  プログラミングでのデッドコードと同じとみなして検出する．

### 表示のイメージ(ユーザ提供の例)

```
文章とは，単語のつながりである．
               (つながり)があるおかげで，文章の構造を明示できる．
                                              (構造)がわかれば，文章を理解しやすくなる．
```

## 段階

1. **R パッケージを完成させる** ← 今ここ
2. Python へ移植する(Streamlit を使う予定)
3. 文章のわかりやすさの判定．段落内での各文の意図を構造化して示し，
   構造化の程度を判定する．ラベルの例:
   トピックセンテンス / 理由 / 補足 / 例示

## 決定事項

- **「同じ単語」の判定**: 形態素解析を通し，名詞・動詞・形容詞などの
  内容語に絞り，**原形(語彙素)で比較**する．
  「つながる」と「つながり」は同一とみなす．助詞・記号は無視する．
- **さかのぼる範囲**: **段落内のすべての先行文**を対象とする．
  ただし**近い文とのつながりほど良い**という基準を加える
  (距離を評価に反映させる)．
- **代表の選び方**: 1つの文が複数の先行文・複数の単語とつながるとき，
  **その文の中でより前方に現れる単語**を代表とする．
  あわせて，**最大3つまでつながりを示せるオプション**を用意する．
- **距離の扱い**: 距離そのもの，または距離の逆数．どちらを使うかはオプションとする．
- **入力**: プレーンテキストと Markdown．
  Markdown はプレーンテキストに変換してから解析する．
  文の区切りはピリオドと句点(`.` `．` `。`)．
- **形態素解析**: ローカル実行が基本(MeCab / Sudachi / Ginza)．
  ネットワークに依存しない構成にする．moranajp を使う．
- **対象言語**: 当面は日本語のみ．
- **デッドコードの検出**: 孤立した文を挙げるだけでなく，
  段落を「単語の共有グラフ」とみなして**連結成分**を数える．
  成分が2つ以上あれば，その段落は話の繋がらない箇所で割れていると判定できる．
  段階3の「構造化の程度」の指標にも使う．
- **パッケージ名**: **`sujimichi`**(筋道)．2026-08-10 決定．
  このパッケージがやることは「文章の筋道が通っているかを見る」ことで，
  デッドコードの検出も「筋道から外れた文を見つける」と説明できる．
  手段(単語のつながり)ではなく目的を指す名前なので，機能が増えても古びない．
  - **CRAN・PyPI ともに空きを確認済み**(2026-08-10)．
    段階2の Python 移植でも同じ名前を使える．
  - 落選した候補: `tsunagari`(次点，両方空き)，`musubime`，`kakehashi`，
    `shiritori`，`mitooshi`，`renbun`，`bunmyaku`，`ronri`．
    `rensa`・`musubi`・`suji`・`nagare` は **PyPI で使用中**のため除外．
    `sujimiti` は `ju`(ヘボン式)と `ti`(訓令式)の混成で，
    海外の利用者に「スジミティ」と読まれるため見送り．
- **置き場所**: 新規リポジトリ `matutosi/sujimichi`(このリポジトリ)．
  - textmining と同居させない理由: あちらの `R/` は Shiny アプリの置き場で，
    `ui.R`/`server.R` はトップレベルで `navbarPage()` を評価する．
    R パッケージの `R/` と衝突し，`R CMD check` が通らない．
  - moranajp に足さない理由: moranajp は形態素解析のパッケージで，
    関心事が違う．依存の向きは `sujimichi` → `moranajp` が自然．
  - 最初は GitHub 配布とし，API が落ち着いてから CRAN に出す．

## 提案(未決)

### 2回目に現れた単語の表示

**表示方法を1つに決めず，コアは表示ではなくデータを返す**設計を提案．

```
文番号 | 語 | 先行文番号 | 距離 | 代表か | 被参照数
```

表示は別関数として段階的に足す．

1. コンソール(インデント揃え + ANSI 色)．
   全角幅は `stringi::stri_width()` で計算する．
2. ggplot2(文を行に並べ，共通語を弧で結ぶ)．最大3本のオプションと相性が良い．
3. HTML(`<span>` に色)．R Markdown / Quarto に貼る用．

**この分離は段階2で効く**．Streamlit ではコンソール向けの桁揃えを持っていけないので，
コアがデータを返す形なら，移植するのは解析部分だけで済む．

「2回目は描画しない(空白)」案は既定にしない(情報が減り，
1文が3つの語でつながるときに空白だらけになる)．オプションとして残す．

### 段階3のラベル付けの手段

3層に分け，**この順序で**進めることを提案．

1. **人手アノテーションを最初に作る**．自分の文章から 30〜50段落を選び，
   トピックセンテンス / 理由 / 補足 / 例示 / その他を手で付ける．
   これが無いと，どの手法でも良し悪しを測れない．
2. **接続表現によるルールベースを既定の実装にする**
   (「たとえば」→例示，「なぜなら・ので・ため」→理由)．
   決定的で依存が軽く，説明可能で，CRAN に出せる．
3. **LLM は任意のバックエンド**(`ellmer` など)として差し替え可能にし，
   **既定にはしない**．ネットワークに依存する既定は，
   まさに moranajp が CRAN からアーカイブされた原因
   (経緯は textmining リポジトリの `.claude/done.md`)．
   使えないときは穏当に失敗させる作りを最初から入れる．

**段階1の成果がそのまま特徴量になる**．トピックセンテンスは
後続の文から多く参照される(入次数が高い)はずなので，
接続表現が無くても構造から推定できる見込みがある．
そのため段階1の返り値に**文ごとの被参照数**を入れておく(上の表の最終列)．

### 進める順序

段階1を最小構成(コアのデータ + コンソール表示 + デッドコード検出)で完成させ，
実際の原稿にかけてみるのが先．「近さの重み」も「最大3つ」も，
実データを見てから調整するほうが早く決まる．
